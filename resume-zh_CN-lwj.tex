\datedsubsection{\textbf{decision first coding agent(AI)}}{2026年}
\role{Python3}{个人项目}
\begin{onehalfspacing}
项目基于一个基本逻辑：一个特化的项目不可能一句话生成，而是由人不断的去做决策和修改最后形成。所以对比目前的chat-first多轮对话的coding agent（human in loop）, 这里提出新的decision first agent范式。新范式把一个项目分成确定性的可ai生成的代码和非确定性的需要人decision的功能（根据置信度），agent会block所有需要decision的代码直到人去做出decision，为了提高decision的效率，agent把项目按模块划分不同的module agent，这样就能高度并行不断生成小decision。对比传统的二层agent架构，这里演化出多module的3层agent。同时系统的输入不再是对话框，而是专用的前端控制台，用户的输入分为一个个模块的小decision，和主入口需求输入，这些输入会持续进入queue等待系统不断处理并生成后续的decision。也就是说，整个repo是由前端decision和输入的需求驱动的。
\begin{itemize}
  \item tool: 相比于传统的代码检索需要多轮搜索需要的代码片段，代码tool使用以下技术：1. 基于静态分析的代码搜索策略（call graph rag），可以一次性搜索出相关代码。2. 使用bm25检索相关的代码片段。3. 基于AST语义片段的本地小模型向量embedding。基于以上联合搜索再使用权重rerank，来实现更高效的代码搜索。
  \item agent: 重新设计coding agent的交互模式。系统角色是3层agent架构，顶层core agent负责所有流程(包含project agent)的管理，每个module由一个project agent管理，project agent是个2层 agent架构，可以使用tool spawn新的sub agent执行具体子任务。每个module的project agent是个tool call loop，同时core agent也是个派发任务的tool call loop。
  \item multi-agent治理流程：从前端收到请求后，会放进后段队列由core agent统一调度。每个module 的project agent是个单独的进程，和core agent使用进程间通信做派发任务和结果返回。core接受队列的请求后拆解任务派发给不同的module 进程，每个module进程接收到请求后，由3个异步模块开启处理：0. main process： 从msg queue里逐个pop请求，不断发布task给agent loop使用。并阻塞等待响应后发给core。 1. msg queue，用来接收core发来的多个消息请求，以及处理decision的阻塞 2. agent loop，接收queue的msg后，agent loop调用tool call loop处理 ，包括spawn subagent，decision tool。3. subagent单独处理的后台任务，完成后统一返回给父agent。
  \item decision tool：当agent loop检测到需要user decision的时候，会block当前module的agent loop并由core agent转发给前端的决策系统。前端反馈后解除block并继续执行。
  \item 前端: 设计专用的前端画布控制台，用户的输入分为一个个模块的小decision，和主入口需求输入，这些输入会进入queue等待系统不断处理并生成后续的decision。
  \item 属性控制：对某些module或代码由特定需求，如安全策略，代码风格，通过前端快速设置，http接口发送给后段设置module 的属性和prompt拼接。
  \item 其他功能：context压缩和长短期记忆拼接。code searching(处理后台长搜索任务的优化)
  \item 项目demo和设计说明：https://github.com/elfcoda/agent-demo

  \end{itemize}
\end{onehalfspacing}
